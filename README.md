## How This Site Was Built — The PAUL Method

This project was built using **PAUL**, a structured framework for working with AI on software development. PAUL was created by [Chris Kahler](https://github.com/ChristopherKahler/paul) and stands for:

> **Plan → Apply → Unify → Loop**

If you want a quick introduction, Chris made a great YouTube video explaining it: [Everyone Uses GSD. Smart Devs Use PAUL](https://youtu.be/MppKHh_MfFc?si=xo9xHId2kjWGnJaB)

---

### The problem PAUL solves

When you use an AI assistant to help build something, a common pattern is to just start asking it to do things — "add this feature," "fix this bug," "make this look better." That works for small, simple tasks. For anything larger, the AI starts to lose track of earlier decisions, contradict itself, or produce work that technically runs but misses the point.

PAUL fixes this by giving the AI (and you) a shared, documented structure to follow. Every piece of work goes through the same three steps.

---

### The three steps

**Plan**
Before anything gets built, you write out what you're going to do and why. You define what "done" looks like before you start. The plan becomes a document that both you and the AI refer to throughout the work. Nothing gets built until the plan is agreed on.

**Apply**
You carry out the plan — making changes, testing them, and adjusting if something doesn't work. Every task is verified against what the plan said it should do. If something unexpected comes up, you stop and revisit the plan rather than improvising.

**Unify**
Once the work is done, you update all the project documents to reflect what actually happened. This includes the roadmap, session notes, and a handoff file that captures what was done, what decisions were made, and what comes next. The goal: anyone — or any AI — could pick up the project cold and know exactly where things stand.

Then you **loop** back to Plan for the next piece of work.

---

### Why this matters

- **It keeps the AI focused.** A written plan gives the AI guardrails and gives you a way to catch mistakes early, before they compound.
- **It eliminates "context rot."** In long AI sessions, output quality degrades as the conversation grows. PAUL's loop structure keeps each session short and purposeful.
- **It makes pausing and resuming easy.** You can stop for days or weeks and pick back up immediately — just read the handoff file.
- **It creates a record.** Every decision has a reason behind it. When you come back later and wonder "why did we do it this way?", the answer is written down.

---

### What's in the `.paul/` folder

The `.paul/` folder holds all the project management documents generated by following this process:

| File | What it is |
|------|------------|
| `STATE.md` | Current milestone, loop position, and key decisions made |
| `ROADMAP.md` | All phases — what's done, what's planned |
| `HANDOFF-*.md` | Session-by-session notes — what was done and what comes next |
| `phases/` | Detailed plan and summary files for each phase |
